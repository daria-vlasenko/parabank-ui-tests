# Чек-лист покрытия и решения об автоматизации

Документ отвечает на вопрос **что покрыто автотестами, что проверяется вручную и на каком основании принято это решение**.

Автотест — дорогой инструмент: написанный один раз, он поддерживается годами. Поэтому сценарий проходит отбор, а не автоматизируется по умолчанию.

Идентификаторы пунктов (ЧЛ-N.N) используются для ссылок из тест-кейсов и отчётов о дефектах.

## Термины

Определения зафиксированы, чтобы столбец «основание» читался однозначно.

**Сквозной сценарий** (end-to-end) — путь пользователя через несколько экранов, затрагивающий больше одной функции. Проверяет работоспособность связки, а не отдельного элемента. Пример из проекта: регистрация → выход → вход под созданным логином → обзор счетов.

**Важность дефекта** — степень ущерба, который нанесёт проекту дефект в этом сценарии:

| Градация | Содержание |
|---|---|
| Критическая | потеря или неверное списание денежных средств, доступ к данным другого клиента |
| Высокая | недоступен основной пользовательский путь, обходной путь отсутствует |
| Средняя | функция работает неверно, обходной путь существует |
| Низкая | неудобство, на достижение цели пользователем не влияет |

**Стоимость поддержки** — объём доработок, которые потребует автотест при изменениях системы. Оценивается по трём признакам: количество локаторов, устойчивость вёрстки в этой области, объём подготавливаемых данных.

**Регресс** — набор тестов, выполняемый перед каждым выпуском для подтверждения того, что ранее работавшая функциональность не нарушена.

**Детерминированный результат** — при одинаковых входных данных сценарий даёт одинаковый исход. Отсутствие детерминированности (внешние системы, таймеры, данные другого прогона) делает автоматизацию ненадёжной.

## Критерии отбора

Сценарий автоматизируется при выполнении не менее двух условий:

- важность дефекта — высокая или критическая;
- сценарий расположен на основном пользовательском пути;
- сценарий входит в регресс;
- результат детерминирован.

Сценарий выполняется вручную, если выполняется хотя бы одно условие:

- результат оценивается субъективно (вёрстка, удобство, читаемость);
- количество комбинаций входных данных делает стоимость поддержки выше получаемой пользы;
- сценарий выполняется однократно при приёмке и в регресс не входит;
- результат не детерминирован.

## Перенос подготовки данных на уровень API

Регистрация клиента и открытие счёта выполняются через интерфейс. Это занимает около семи секунд на прогон и создаёт зависимость: сценарий перевода перестанет выполняться при нарушении формы регистрации, хотя проверяет операцию перевода.

У тестируемого приложения есть REST API. Планируемое решение — создавать клиента и счёт одним HTTP-запросом, интерфейс использовать только для проверяемой операции. Этап включён в план проекта.

Принцип: **через интерфейс проверяется интерфейс**. Проверка, выполнимая на нижележащем уровне, выполняется на нижележащем уровне — там выше скорость, выше стабильность, ниже стоимость поддержки.
