# Чек-лист покрытия и решения об автоматизации

Документ отвечает на вопрос **что покрыто автотестами, что проверяется руками и почему именно так**.

Автотест — дорогой инструмент: написанный один раз, он поддерживается годами. Поэтому каждый сценарий проходит отбор, а не автоматизируется по умолчанию.

## Критерии отбора

Сценарий автоматизируется, когда выполняются хотя бы два условия:

- **высокая цена ошибки** — деньги, доступ, потеря данных
- **высокая частота использования** — критичный пользовательский путь
- **повторяемость** — сценарий прогоняется в каждом регрессе
- **стабильный результат** — поведение детерминировано, не зависит от восприятия

Сценарий остаётся ручным, когда:

- **проверка субъективна** — вёрстка, удобство, читаемость
- **комбинаторный взрыв** — десятки полей × десятки значений, стоимость поддержки не окупается
- **сценарий разовый** — проверяется один раз при приёмке и больше не повторяется
- **поведение нестабильно** — внешние зависимости, таймеры, капча

## Аутентификация и регистрация

| Сценарий | Уровень | Почему так |
|---|---|---|
| Главная открывается, форма входа отображается | UI-автотест | smoke: если сломано это, остальное проверять бессмысленно |
| Вход с пустыми полями → сообщение об ошибке | UI-автотест | негативный путь, дёшев, стабилен |
| Регистрация нового клиента | UI-автотест | предусловие для всех остальных сценариев |
| Зарегистрированный пользователь входит | UI-автотест | ключевой путь, ломается чаще всего при релизах |
| Выход из системы | UI-автотест (план) | завершает сквозной сценарий, дёшев |
| Вход с неверным паролем | **исключён** | стенд принимает любые данные — см. `bug-reports.md`, DEF-001 |
| Валидация каждого из 11 полей регистрации | руками | 11 полей × 4 класса значений ≈ 44 проверки; поддержка не окупается при редких изменениях формы |
| Маска и формат телефона, SSN, индекса | руками | комбинаторика значений, проверяется один раз при приёмке формы |
| Вёрстка формы на разных разрешениях | руками | визуальная проверка, автоматизация требует отдельного инструмента сравнения скриншотов |

## Счета

| Сценарий | Уровень | Почему так |
|---|---|---|
| Открытие нового счёта | UI-автотест (план) | предусловие для переводов, повторяется в каждом регрессе |
| Обзор счетов: счёт отображается, баланс совпадает | UI-автотест (план) | проверка данных, результат детерминирован |
| История операций по счёту | UI-автотест (план) | подтверждает, что операция дошла до хранилища |
| Сортировка и постраничный вывод в таблице счетов | руками | низкая цена ошибки, высокая стоимость автоматизации таблиц |

## Переводы

| Сценарий | Уровень | Почему так |
|---|---|---|
| Перевод между своими счетами | UI-автотест (план) | денежная операция — максимальная цена ошибки |
| Баланс обоих счетов изменился на нужную сумму | UI-автотест (план) | главная проверка перевода; без неё тест бессмыслен |
| Перевод суммы больше остатка | UI-автотест (план) | негативный путь с высокой ценой ошибки |
| Перевод нулевой и отрицательной суммы | руками | граничные значения, проверяются один раз |
| Округление копеек при переводе | руками, затем API | проверка расчёта, не интерфейса — уровень UI для неё избыточен |

## Поиск транзакций

| Сценарий | Уровень | Почему так |
|---|---|---|
| Поиск по сумме находит совершённый перевод | UI-автотест (план) | замыкает сквозной сценарий «перевёл → нашёл» |
| Поиск по диапазону дат | руками | зависит от данных на стенде, нестабилен |
| Поиск по идентификатору транзакции | API | проверяет логику поиска, а не интерфейс |

## Что стоило бы перенести на уровень API

Отдельный вывод, важный для планирования.

Подготовка данных — регистрация клиента и открытие счёта — сейчас выполняется через интерфейс. Это **медленно** (около семи секунд на прогон) и **хрупко**: тест перевода упадёт из-за поломки формы регистрации, хотя проверяет совсем другое.

У ParaBank есть REST API. Правильный следующий шаг — создавать клиента и счёт одним HTTP-запросом, а браузер использовать только для того, что собственно проверяется. Это заложено в план проекта как отдельный этап.

Общий принцип: **через интерфейс проверяют интерфейс**. Всё, что можно проверить уровнем ниже, проверяют уровнем ниже — там быстрее, стабильнее и дешевле в поддержке.
