# ParaBank UI Tests

[![CI](https://github.com/daria-vlasenko/parabank-ui-tests/actions/workflows/ci.yml/badge.svg)](https://github.com/daria-vlasenko/parabank-ui-tests/actions/workflows/ci.yml)

UI-автотесты демо-приложения интернет-банка [ParaBank](https://parabank.parasoft.com/parabank/index.htm) — учебного стенда Parasoft для практики тестирования.

Проект — часть портфолио по автоматизации тестирования. Смежные репозитории: [conduit-api-tests](https://github.com/daria-vlasenko/conduit-api-tests) (API, REST Assured), [java-testing-practice](https://github.com/daria-vlasenko/java-testing-practice) (unit, JUnit 5 + Mockito).

> **Статус: завершён.** Покрыт сквозной пользовательский путь — регистрация, вход, открытие счёта, перевод между счетами, выход. Найдено три дефекта. Остальные проверки разнесены по уровням с обоснованием в [чек-листе](docs/test-checklist.md).

## Стек

| Компонент | Назначение |
|---|---|
| Java 17 | язык |
| Maven | сборка и запуск |
| Selenide 7.9.3 | работа с браузером, умные ожидания |
| JUnit 5 | тестовый движок |
| Allure | отчётность, скриншоты при падении |
| GitHub Actions | прогон в headless-браузере на каждый push |

## Запуск

```bash
mvn clean test                    # прогон с видимым браузером
mvn clean test -Dheadless=true    # прогон без окна браузера
mvn allure:serve                  # собрать отчёт и открыть в браузере
```

Браузер переключается параметром: `-Dbrowser=firefox`. По умолчанию Chrome.

## Как распределены проверки по уровням

UI-автотест поддерживается весь срок жизни проекта, поэтому проверка проходит отбор, а не автоматизируется по умолчанию.

| Уровень | Что сюда попадает | Почему |
|---|---|---|
| **UI-автотест** | сквозные пользовательские пути: регистрация, вход, счёт, перевод, выход | высокая цена ошибки, повторяется в каждом регрессе |
| **Уровень API** | валидация форматов, округление, поиск транзакций, история операций | не требует интерфейса; через API быстрее, стабильнее и покрывает больше комбинаций |
| **Вручную** | вёрстка при узком окне, граничные значения логина, валидация формы регистрации | субъективная оценка или комбинаторика, где поддержка дороже пользы |

Проверки, которые в рабочем проекте автоматизируют на другом уровне, помечены как `Уровень API`, а не отнесены к ручным. Формулировка «делается руками» оставлена только там, где это действительно так.

## Найденные дефекты

Оформленные отчёты — в [`docs/bug-reports.md`](docs/bug-reports.md).

### DEF-001: обход аутентификации

Негативный тест на вход с неверными учётными данными упал. Разбор показал, что **стенд принимает любую непустую пару логин-пароль** и выдаёт авторизованную сессию со случайным счётом. Проверка на заполненность полей работает, сверки с хранилищем учётных данных нет.

| | |
|---|---|
| **Шаги** | открыть `index.htm`, ввести несуществующий логин и произвольный пароль, нажать `Log In` |
| **Ожидалось** | сообщение «The username and password could not be verified.» |
| **Фактически** | переход на `overview.htm`, пользователь авторизован |
| **Severity** | Critical — обход аутентификации в банковском приложении |
| **Классификация** | OWASP A07 Identification and Authentication Failures, CWE-287 |

**Сценарий не включён в набор:** заведомо красный тест без привязки к дефекту — шум, на который команда перестаёт реагировать. Вместо него в наборе негативный кейс на пустые поля.

### DEF-002: перевод сверх остатка

Проверка родилась из вопроса, на каком допущении держится форма перевода: она предполагает, что у клиента есть деньги. Попытка перевести больше доступного остатка показала, что проверки нет.

| | |
|---|---|
| **Шаги** | зарегистрироваться, открыть второй счёт, перевести сумму больше остатка |
| **Ожидалось** | отказ, балансы не изменились |
| **Фактически** | «Transfer Complete!», списано $1415.50 при остатке $415.50, баланс ушёл в `-$1000.00` |
| **Severity** | High — овердрафт без договора в банковском приложении |
| **Классификация** | нарушение бизнес-правила предметной области |

**Тест остался в наборе в изменённой формулировке.** Вместо «ожидаем отказ» он фиксирует фактическое поведение: сколько было, сколько перевели, сколько стало. Тест зелёный, помечен `@Issue("DEF-002")` и покраснеет, если дефект когда-нибудь исправят.

### DEF-003: изображение без альтернативного текста

Осмотр страницы через дерево доступности DevTools показал, что изображение-иконка в шапке (`img.admin`) не имеет атрибута `alt`: у элемента с ролью `image` пустое имя (`name: null`), а встроенная проверка браузера сообщает об отсутствии альтернативного текста.

| | |
|---|---|
| **Шаги** | открыть `index.htm`, DevTools → вкладка доступности, найти узел `image` (`img.admin`), проверить `name` |
| **Ожидалось** | у изображения задан осмысленный `alt`, имя в дереве доступности непустое |
| **Фактически** | `name: null`; скринридер не сообщает назначение изображения |
| **Severity** | Low — не нарушает функциональность, страдает доступность |
| **Классификация** | WCAG 2.1 SC 1.1.1 «Non-text Content» (уровень A) |

**Найдено вручную, автотестом не покрыто.** Кандидат на автоматическую проверку доступности (axe-core) в CI, которая выявляла бы подобные нарушения на каждом прогоне.

Все три дефекта найдены **без спецификации** — у демо-стенда её нет. Оракулом служили общие правила предметной области и стандарты: как обязана работать аутентификация, что баланс не уходит в минус без договора, что изображение должно иметь альтернативный текст по WCAG.


## Принятые решения

**Page Object.** Локаторы живут в классах-страницах, в тестах нет ни одного селектора. Правка разметки сайта чинится в одном месте, а не в каждом тесте.

**Page Component.** Левое меню вынесено в отдельный класс `LeftPanel`: оно присутствует на всех страницах после входа, дублировать его в каждом Page Object бессмысленно.

**Деньги на `BigDecimal`.** Балансы читаются и сравниваются в `BigDecimal`, а не в `double`: двоичное представление не хранит десятичные дроби точно, и сравнение балансов периодически падало бы на копейках. Сравнение — через `compareTo`, а не `equals`: у `BigDecimal` `equals` учитывает ещё и количество знаков после запятой, поэтому `100.00` и `100.0` по нему не равны.

**Перевод проверяется арифметикой, а не текстом.** Страница подтверждения сообщает о принятии операции, но не о её результате. Тест возвращается в обзор счетов и сверяет оба баланса.

**Выход проверяется на сервере.** Отдельный тест открывает закрытую страницу по прямому адресу после выхода. «Логаут только на клиенте» — известный класс уязвимостей, и проверка появления формы входа его не ловит.

**Порядок шагов выведен из поведения системы.** Открытие нового счёта в ParaBank переносит на него $100 с существующего, поэтому балансы фиксируются после открытия второго счёта. Иначе арифметика не сходится и тест падает по причине, не связанной с переводом.

**Локатор описывает смысл, а не внешний вид.** Кнопка перевода ищется как `#rightPanel input[type='submit']` — по роли и месту в структуре, а не по надписи. Переименование кнопки или перевод интерфейса такой локатор не ломают.

**Уникальные данные вместо фикстур.** `TestDataFactory` генерирует клиента с уникальным логином на каждый прогон. Стенд общий и запоминает регистрации, поэтому фиксированные данные сработали бы ровно один раз.

**Никаких `Thread.sleep`.** Только условия Selenide с перепроверкой до таймаута.

**Поиск по атрибуту вместо экранирования.** У полей формы регистрации идентификаторы содержат точку (`customer.firstName`), а в CSS точка означает класс. Вместо `#customer\\.firstName` используется `input[id='customer.firstName']` — то же самое, но без экранирования и связанных с ним ошибок.

**Java 17, не 25.** На Java 25 не стартует агент AspectJ, из-за чего Allure перестаёт записывать шаги внутри тестов. Версия зафиксирована и локально, и в CI.

**Раздельные версии Allure.** `allure-java` (библиотека) и `allure-commandline` (утилита сборки отчёта) выпускаются независимо, поэтому в `pom.xml` разведены в два свойства.

**Транзитивная зависимость с уязвимостью переопределена.** `commons-lang3` поднят до 3.20.0 через `dependencyManagement` — закрывает CVE-2025-48924.

**Одинаковые переводы строк.** `.gitattributes` с `* text=auto eol=lf`: в репозитории файлы хранятся с LF независимо от операционной системы автора. Без этого коммит с Windows перезаписывает каждую строку файла, и настоящее изменение теряется среди шума на ревью.

## CI

При каждом push и pull request в `main` GitHub Actions поднимает Ubuntu, ставит JDK 17 и прогоняет тесты в headless-Chrome.

Результаты Allure сохраняются артефактом прогона всегда, через `if: always()` — без этого флага при падении тестов не сохранились бы именно те данные, ради которых всё настраивалось. Скриншоты Selenide прикладываются только при падении. Скачать артефакты можно со страницы конкретного запуска во вкладке `Actions`.
